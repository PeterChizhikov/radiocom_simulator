## 1. Цель и принятые решения

Система для двусторонней линии связи между базовой станцией (БС, eNodeB) и абонентом (UE) на двух Pluto SDR по мотивам
LTE: собственный упрощённый физический уровень, повторяющий LTE Rel-8 там, где это возможно, и упрощённый протокол
подключения абонента к БС. Программного симулятора больше нет: он был удалён, все результаты получаются через эфир.
Отчётные материалы (графики BER/BLER от SNR, измерения для курсовой) делаются **после** того, как система заработает.

| Параметр | Решение |
|---|---|
| Язык | C++20, весь код ядра |
| Уровни | физический уровень + упрощённый протокол подключения абонента к БС |
| Дуплекс | TDD, кадр типа 2 (TS 36.211 V16.2.0, 4.2): время делится между приёмом и передачей на одной частоте. Ранее FDD отклонили при одной антенне на каждом Pluto; после добавления антенн сохраняем выбранный TDD |
| Скорости и тайминги | на скорости и задержки LTE не ориентируемся: Pluto работает через USB с плавающей задержкой и без меток времени, поэтому расписание субкадров D/U по эфиру точно не выдерживается. Формат кадра делаем по стандарту, а обмен по направлениям — пинг-понгом |
| Порядок обмена | по очереди: один Pluto передаёт, другой принимает, затем наоборот. Одновременной передачи и приёма на одном Pluto нет |
| Оборудование | два Pluto, с 14.11.2026 на каждом отдельные антенны TX1 и RX1 (всего четыре). Через разъём без антенны не передаём и не принимаем |
| Работа по эфиру | пинг-понг «передал, переключился, принял» (см. раздел 9); жёсткая сетка субкадров по времени на Pluto невозможна, так как данные идут через USB с плавающей задержкой |
| Полезная нагрузка | тестовые данные, не реальный IP-трафик |
| Работа с SDR | libiio (C API) напрямую |
| Частота | 2.4 ГГц (ISM) |
| Полоса и частота дискретизации | LTE 3 МГц: 3.84 MSPS, БПФ 256, 180 поднесущих |
| Мощность передачи | начинать с минимальной, поднимать шагами по 10 дБ; ослабление TX от 0 до 89.75 дБ (нижний предел 40 дБ снят 08.11.2026) |
| Готовые библиотеки | кодирование берём готовое: AFF3CT (MIT) для турбокода; своё не пишем |
| Процессы | одна программа, роль выбирается флагом (`--role bs` или `--role ue`), один процесс на каждый Pluto |
| Подход | двигаться маленькими шагами, каждый проверять по эфиру или независимым эталоном; формулы и константы брать из стандарта и записывать пункт в комментарии |

**Состояние этапа на 14.11.2026:** автоматический последовательный эхо-обмен реализован и проверен
на двух Pluto с четырьмя антеннами TX1/RX1. Формат сообщений, настройки и ограничения описаны в разделе 3,
измерения переключения и результаты — в разделе 7, дальнейшие этапы — в разделе 9.
Решения и план ведутся в этом документе; отдельные документы проекта и плана дуплексного обмена удалены.
Работы на текущем этапе остановлены по указанию пользователя; дальнейшие изменения — после обсуждения.

UI (веб-интерфейс) планировался раньше, сейчас не развивается.

## 2. Оборудование и безопасность

Два ADALM-Pluto, подключены к одному компьютеру по USB, антенны на расстоянии нескольких сантиметров:

| Роль | Чип | Серийный номер | URI на 18.10.2026 | URI на 08.11.2026 | Антенна |
|---|---|---|---|---|---|
| Передатчик (БС) | AD9361, 2x2 | `104000409f94…` | `usb:1.3.5` | `usb:1.4.5` | TX1 |
| Приёмник (UE) | AD9364, 1x1 | `10400090fd95…` | `usb:1.4.5` | `usb:1.5.5` | RX1 |

- **URI меняются** после переподключения. Роли определять по серийным номерам: `iio_info -s`.
- В документах `pluto_info.md` и `sdr_txrx_test.md` URI одного и того же серийного номера записаны по-разному, так как
  снимались в разное время. Верить текущему выводу `iio_info -s`.
- Один раз Pluto-передатчик перестал открываться (`Failed to reset pipes: Input/output error`) после серии быстрых
  запусков и остановок передачи. Помогло переподключение USB.
- Расхождение частот двух Pluto около **−12.5 кГц** на 2.4 ГГц (около −5 ppm), почти одна поднесущая (15 кГц).
  Дрейф по температуре в больших интервалах не измерялся.
- Расстояние между антеннами критично: разведение антенн ухудшает связь примерно на **20 дБ** (тон падал с 54 дБ до
  33 дБ над шумом при том же ослаблении).

**Защита приёмного тракта** (в `Sdr.cpp`, не отключать): при старте ослабление TX ставится на максимум (89.75 дБ),
при выходе передача останавливается и ослабление возвращается на максимум. Повредить
вход приёмника может только мощность на входе RX; усиление RX влияет лишь на клиппинг АЦП. Нижний предел ослабления
40 дБ снят 08.11.2026 по решению автора проекта: при 40 дБ и разнесённых антеннах сигнал слишком слаб. Теперь
допустимо 0…89.75 дБ; мощность по-прежнему поднимать шагами по 10 дБ и следить за клиппингом на приёме.

## 3. Структура проекта и как запускать

Все модули в `src/modules/<Модуль>/`: заголовок и `.cpp` рядом, один CMake-таргет на модуль.

| Модуль | Назначение |
|---|---|
| `Common` | типы `Sample_t`, `Signal_t`, `Bytes_t` |
| `Logger` | интерфейс `ILogger`, реализация на spdlog |
| `SignalFileIO` | сохранение и загрузка I/Q в файл (float32, как `gr_complex`), нужно для разбора записей `rx.iq` |
| `SignalManipulation` | физический уровень: интерфейс `IPhyLayer` (`Modulate`, `FindSync`, `Demodulate`, `GetPayloadSize`); файлы: `Ofdm` — сетка, PSS, CRS, оценка канала, OFDM-модем; `ChannelCoding` — CRC24A/CRC24B, сегментация, таблицы MCS и TBS, турбокод, согласование скорости, скремблирование, QPSK/16QAM/64QAM и мягкий демаппер; `SignalManipulation.cpp` — класс `PhyLayer` с синхронизацией |
| `Sdr` | `PlutoDevice`: настройка и передача/приём через libiio |
| `Link` | последовательный эхо-обмен: `Link.h/.cpp` — управление TX/RX, ожидание и повторы; `LinkPacket.h/.cpp` — формат запроса/ответа, сеанс и номер запроса |
| `src/main.cpp`, `src/Run.cpp` | запускатель системы с ролями `bs` и `ue`: в `main.cpp` только вызов, разбор аргументов и роли в `Run.cpp` |
| `src/txrx.cpp` | первый аппаратный тест: передача и приём тона |

Сборка (при первой конфигурации нужна сеть: скачиваются spdlog и AFF3CT; AFF3CT добавляет около полутора минут к
чистой сборке):

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release        # -DRADIOCOM_WARNINGS_AS_ERRORS=ON, чтобы предупреждения были ошибками
cmake --build build
```

Запуск (передатчик в одном терминале, приёмник в другом; передача идёт, пока не нажат Enter):

```bash
./build/radiocom --role bs --uri usb:1.3.5 --tx-atten 40
./build/radiocom --role ue --uri usb:1.4.5 --rx-gain 50 --output rx.iq
./build/radiocom --role bs --uri usb:1.3.5 --tx-atten 20 --mcs 17   # 64QAM; --mcs одинаковый у bs и ue
./build/radiocom_txrx --tx usb:1.3.5 --rx usb:1.4.5 --tx-atten 50 --rx-gain 50   # тест с тоном
```

`ue` выводит: уровень приёма, начало слота и сдвиг частоты, число ошибок кодовых бит до декодирования и признак
«CRC верна, сообщение верное». Ключ `-v` включает подробный журнал.

Зависимости: CMake, компилятор C++20, FFTW3 (`brew install fftw`), libiio (`brew tap tfcollins/formulae &&
brew install libiio`; на macOS поиск через `find_library`, так как `libiio.pc` сломан), spdlog и AFF3CT скачиваются сами.

### Автоматический двусторонний обмен (14.11.2026)

Новый режим `--exchange`: БС передаёт запрос, выключает TX и принимает; UE принимает запрос и возвращает
его данные с типом «ответ». БС проверяет CRC, сеанс, номер и все байты эха. По одному процессу на Pluto,
обмен между процессами идёт только по эфиру. Старый режим без `--exchange` сохранён.

Команды для текущего подключения (перед запуском проверить URI через `iio_info -s`):

```bash
# Сначала UE (fd95), затем в течение 10 секунд БС (409f94) в другом терминале
./build/radiocom --role ue --uri usb:0.3.5 --exchange --count 100 --mcs 0 --tx-atten 10 --rx-gain 40
./build/radiocom --role bs --uri usb:0.4.5 --exchange --count 100 --mcs 0 --tx-atten 20 --rx-gain 40
```

`--count` — число разных запросов (по умолчанию 100). По уточнению пользователя от 14.11.2026
ARQ/HARQ отложены: на каждый запрос допускается только одна попытка. Аргумент `--attempts` сохранён
для совместимости команд, но принимает только 1; значение по умолчанию — 1. Дубликаты уже обработанного
запроса UE игнорирует и не отправляет ответ повторно. MCS и `--count` должны совпадать у сторон.

Пачка передачи — 500 мс повторяющихся кадров. UE ждёт 600 мс после декодирования запроса перед ответом,
БС — 600 мс после декодирования ответа перед следующим запросом. Это запас для остатка пачки и USB,
а не соблюдение расписания LTE в реальном времени. БС ждёт корректный ответ 3 секунды после завершения TX.
UE обслуживает один сеанс БС и выходит после 10 секунд без корректного запроса, в том числе после последнего
ответа. Для нового запуска БС перезапустить также UE.
Код завершения 0 означает выполнение заданного числа обменов; тайм-аут ответа/ошибка/прерывание — 1.
Ctrl+C и SIGTERM в этом режиме останавливают цикл, затем TX и возвращают максимальное ослабление при выходе.
Отдельная IIO-операция ограничена тайм-аутом 1000 мс.

20-байтный заголовок проекта: `RCOM`, версия 1, тип 1/2, два нулевых байта, 64-битный сеанс и 32-битный
номер в сетевом порядке байтов. Остаток транспортного блока — данные эха (29 байт при MCS 0).
Один пакет повторяется во всех четырёх транспортных блоках кадра. Если один блок проходит CRC,
он принимается самостоятельно. Иначе мягкие значения четырёх копий объединяются внутри этого кадра,
после индивидуального дескремблирования и обратного согласования скорости; результат также проверяется CRC.
Такое объединение уже переданных копий отдельно разрешено пользователем. Накопления между кадрами,
новых отправок по результату ошибки и ARQ/HARQ нет. Обычный `Demodulate` продолжает независимо
декодировать субкадры с разными нагрузками; для Link добавлен явный `DemodulateRepeatedPayload`.
Временное упрощение: существующий PHY используется в обе стороны, полноценного LTE PUSCH пока нет.

Пользователь разрешил повышать мощность при необходимости: уменьшать ослабление TX шагами по 10 дБ и
контролировать клиппинг. Автоматическая регулировка мощности не добавлялась: TX attenuation и RX gain
задаются отдельно у каждого устройства. По указанию пользователя автоматические тесты не добавляются;
проверка — сборка, реальные эфирные запуски, журналы и небольшое число графиков.

## 4. Что сделано и проверено

Порядок соответствует хронологии работы.

1. **Тон через эфир** (этап 1). Управление Pluto из C++, циклическая передача тона +100 кГц, приём 65536 отсчётов, поиск
   пика в спектре. Измерен сдвиг частоты между двумя Pluto. Результаты в `sdr_txrx_test.md`.
2. **Симулятор убран.** Удалены `SimulationCore`, канал AWGN, цикл по SNR, `plotBER_SBR.py`. `main.cpp` стал
   запускателем ролей. Модуль `SignalManipulation` разделён на «байты в отсчёты» и «отсчёты в байты».
3. **Первый кадр через эфир** (Хэмминг, QPSK, один OFDM-символ). Показал, что кадр слабый (около −30 дБFS из-за
   деления на N при IFFT); `main.cpp` теперь масштабирует передаваемый кадр до пика 0.5, как у проверенного тона.
4. **Сигнал синхронизации PSS** (Задова–Чу, корень 25, 62 элемента) и поиск кадра кросс-корреляцией. По эфиру находится.
5. **Оценка сдвига частоты.** Сдвиг смещает пик корреляции Задова–Чу по времени (около 100–150 отсчётов при 12 кГц),
   поэтому сначала перебираются гипотезы сдвига от −15 до +15 кГц с шагом 3 кГц, затем уточнение по разности фаз
   корреляций двух половин PSS. Точность оценки в синтетике: меньше 50 Гц; по эфиру −12.2…−12.8 кГц.
6. **Сетка LTE на 3 МГц и слот.** 15 RB, 180 поднесущих (−90…−1, +1…+90, DC пустая), слот из 7 символов,
   CP 20 у символа 0 и 18 у остальных, слот 1920 отсчётов. PSS в последнем символе слота (как в LTE FDD).
7. **Пилоты CRS и оценка канала.** Пилоты порта 0 в символах 0 и 4, каждая 6-я поднесущая (в символе 4 со сдвигом 3),
   значения из последовательности Голда. Оценка канала: деление принятого на известное в пилотах, интерполяция по
   частоте, затем по времени между символами 0 и 4. Убрало случайный поворот созвездия (до этого 15–50 % ошибок).
8. **Турбокод LTE** через AFF3CT вместо Хэмминга. Цепочка: CRC24A, турбокод, согласование скорости, скремблирование,
   QPSK. На приёме мягкие значения, обратные операции, декодер AFF3CT (6 итераций), проверка CRC.
9. **Хэмминг удалён** (код и файл `Hamming.h`).
10. **16QAM и 64QAM, все MCS 0–28** (08.11.2026). Отображение по TS 36.211 V16.2.0, табл. 7.1.3-1 и 7.1.4-1 (общая
    функция `mapBits` для Q_m = 2, 4, 6: по каждой оси код Грея, первый бит задаёт знак; нормировка 1/√2, 1/√10, 1/√42).
    Мягкий демаппер max-log по каждой оси: LLR = |H|²·(min по точкам с битом 1 − min по точкам с битом 0)/(2σ²) в
    выровненной области Y/H; для QPSK совпадает с прежней формулой. Для MCS 21–28 (TBS 6456–11064 бит) транспортный
    блок делится на 2 кодовых блока с CRC24B (TS 36.212 V15.2.1, 5.1.2), длины E_r — по 5.1.4.1.2 (⌊G′/C⌋ или ⌈G′/C⌉),
    выходы блоков склеиваются по 5.1.5. Приём принимает блок, только если сошлись все CRC24B и CRC24A. Проверено по
    эфиру вплоть до MCS 28 (раздел 7).

## 6. Допущения, не взятые из стандарта

Эти места нужно знать и при необходимости сверить:

- **Порядок бит в байте нагрузки:** старший бит первым. В присланных страницах порядок не определён.
- **n_RNTI = 1:** значение выбрано в проекте.
- **N_cb = K_w:** размер кольцевого буфера принят полным; формула с N_IR (мягкий буфер приёмника по категории UE) в
  проекте не применялась (5.1.4.1.2).
- **6 итераций** турбодекодера выбраны в проекте.
- **Мягкий демаппер max-log** и оценка σ² по расстоянию до ближайшей точки — выбор проекта (в стандарте приём не
  описан). На слабом сигнале σ² по ближайшей точке занижена, для 64QAM сильнее, чем для QPSK.
- **Только кодовые блоки одной длины** (F = 0, C₋ = 0): для всех TBS из столбца N_PRB = 15 это выполняется.

Отображение QPSK (b(i) задаёт I, b(i+1) задаёт Q, 0 даёт плюс) сверено 08.11.2026 с табл. 7.1.2-1 TS 36.211 V16.2.0
и из списка допущений убрано.
- **Номер слота n_s = 0 всегда:** передаётся один и тот же слот, поэтому CRS и скремблирование не меняются.
- **Одна ячейка:** N_ID^cell = 0, корень PSS 25. В символе с PSS остальные поднесущие не несут данных (в LTE они могут
  быть заняты PDSCH, правила в 36.211 6.3.5 не изучались).
- **Размер E:** все 1020 ресурсных элементов слота отданы под один кодовый блок; в LTE слот был бы частью субкадра из
  двух слотов, PBCH и управляющие каналы не учитываются.
- **Размер блока и частота 3.84 МГц:** инженерное соглашение (отчёт, п. 4.6).

### Диагностика оценки канала и мягких решений (14.11.2026)

Продолжение поиска причины на тех же 18 сохранённых окнах UE → БС, без новых передач и без изменения
рабочего кода. Во временной копии PHY менялась только оценка канала либо общий масштаб LLR;
декодирование, CRC и сравнение всех байтов нагрузки оставались штатными. Базовый вариант воспроизвёл
результаты предыдущей диагностики.

В штатном оценивателе `estimateChannel` отношение принятого CRS к известному значению напрямую
интерполируется по частоте и времени, без усреднения соседних пилотов. При слабом сигнале шум
пилотов попадает в оценку амплитуды и фазы канала и далее в демаппер.

Диагностические варианты:

- усреднение CRS по частоте в пределах ±12 поднесущих отдельно для каждого из четырёх пилотных символов;
  затем прежняя интерполяция/экстраполяция по времени. Полезные данные для оценки канала не используются;
- усреднение CRS одновременно по частоте и по всем четырём пилотным символам с постоянной оценкой
  канала в субкадре — чувствительно к остаточной частотной ошибке;
- оптимистичная оценка по всем известным переданным символам отдельно для каждой поднесущей,
  с дополнительной подгонкой общей фазы каждого OFDM-символа. Это оценка по тем же данным, на которых
  проверяется результат; её нельзя считать готовым рабочим алгоритмом или строгой границей качества;
- умножение всех штатных LLR на 0.125, 0.25, 0.5, 1, 2 и 4 без изменения оценки канала.

**Со штатными началом кадра и частотной оценкой, 20 дБ ослабления TX:**

| Вариант | MCS 16 | MCS 17 |
|---|---|---|
| Штатный приём | 0/12 | 0/12 |
| Усреднение CRS по частоте отдельно в каждом пилотном символе | 6/12 | 0/12 |
| Постоянная оценка по CRS с усреднением также по времени | 5/12 | 0/12 |
| Изменение только общего масштаба LLR, все шесть значений | 0/12 | 0/12 |

На 10 дБ вариант с усреднением CRS по частоте поднял MCS 16 с 11/12 до 12/12, MCS 17 остался 12/12.
Контрольный QPSK/MCS 0 сохранил 12/12 при обоих ослаблениях.

**При независимой частотной/временной оценке по известному кадру, 20 дБ:** усреднение CRS
одновременно по частоте и времени дало 11/12 на MCS 16 и 0/12 на MCS 17. Оптимистичная оценка
по всем известным данным с подгонкой фазы каждого символа — 12/12 и 4/12 соответственно.
Одно только исправление общей фазы поверх штатной оценки канала не восстановило блоки при 20 дБ.

Вывод: для MCS 16 подтверждена существенная потеря из-за шумной оценки канала по CRS.
Только FindSync или общий масштаб LLR не объясняют отказ. Усреднение по времени нельзя переносить
в программу без учёта остаточного вращения фазы: даже небольшая частотная ошибка меняет канал за субкадр.
Для MCS 17 улучшение канала само по себе в проверенных вариантах не обеспечило надёжный приём;
качество сигнала обратной линии около 7 дБ S/(шум + помехи) остаётся существенным ограничением.
Это не доказательство отсутствия других резервов демаппера/декодера.

Следующее предлагаемое изменение — усреднение CRS по частоте с сохранением временной структуры,
после согласования проверить его на свежих эфирных запусках. Рабочий `Ofdm.cpp` этой диагностикой не менялся.

### Реализация частотного усреднения CRS и сравнение по эфиру (14.11.2026)

на краях полосы; используется фактическое число пилотов. Прежняя временная интерполяция/экстраполяция

### Совместная оценка фазы/канала и объединение копий в кадре (14.11.2026)

Пользователь уточнил границы этапа: ARQ/HARQ и новые отправки по результату ошибки запрещены,
объединять уже переданные копии внутри одного кадра разрешено. Эти ограничения отражены в программе:
по умолчанию одна попытка на запрос, CLI и Link отвергают `--attempts` больше 1, дубликаты запроса
игнорируются без нового ответа. Все измерения ниже выполнены с `--count 1 --attempts 1` либо
одной попыткой на каждое из десяти последовательных сообщений.

В `Ofdm.cpp` сохранено частотное усреднение CRS и добавлена оценка вращения фазы: комплексные
оценки четырёх пилотных символов сравниваются с первым, фаза разворачивается и аппроксимируется
линейно по времени. После снятия этого вращения оценки канала усредняются между пилотными символами,
затем фаза восстанавливается для каждого OFDM-символа. Это проектная модель постоянного частотного
отклика и линейного изменения общей фазы за 1 мс; полноценное сопровождение быстрого изменения
канала не реализовано. На сохранённых записях MCS 16 при 20 дБ это дало 11/12 блоков вместо 6/12
у одного частотного усреднения. MCS 17 при 20 дБ по отдельным блокам остался 0/12.

У Link уже передавался один и тот же пакет во всех четырёх транспортных блоках кадра. Прежде
каждый блок декодировался независимо. Теперь в явном методе `DemodulateRepeatedPayload`:

1. Каждый субкадр демодулируется со своей оценкой канала и скремблирующей последовательностью.
2. Если отдельный транспортный блок проходит все CRC, его нагрузка принимается сразу.
3. Если ни один блок не принят отдельно, мягкие значения складываются после дескремблирования
   и обратного согласования скорости, отдельно для каждого кодового блока.
4. Совместный результат декодируется и проверяется по CRC24B (при сегментации) и CRC24A.

Накопитель локален одному вызову и одному кадру 10 мс, между кадрами ничего не переносится.
Обратная связь для повторов отсутствует, передаваемый сигнал, мощность, длительность пачки и MCS
не изменены. Это использование существующей избыточности эхо-кадра, не реализация LTE HARQ.
Обычный `Demodulate` сохранён для независимых транспортных блоков с разными нагрузками.

На тех же сохранённых I/Q совместная рабочая реализация восстановила пакет в 3/3 окнах для каждого
MCS 0/16/17 при 10 и 20 дБ. Для MCS 17 при 20 дБ отдельные блоки не проходили CRC, но объединённый
пакет восстанавливался. Эти числа относятся к пакетам из четырёх копий, не к независимым блокам.

Свежий эфир: старый вариант (только частотное усреднение, без объединения) чередовался с новым.
Ослабление обоих TX одинаковое, RX gain 40 дБ; по три независимых эхо на вариант:

| MCS | Ослабление TX | Старый вариант, эхо | Совместный вариант, эхо |
|---|---|---|---|
| 16 | 20 дБ | 0/3 | 3/3 |
| 17 | 20 дБ | 0/3 | 3/3 |
| 0 | 20 дБ | 3/3 | 3/3 |
| 16 | 10 дБ | 3/3 | 3/3 |
| 17 | 10 дБ | 3/3 | 3/3 |

Всего 30 обменов за 93.4 с, клиппинга не отмечено. После окончательного отключения обработки
дубликатов выполнены отдельные подтверждающие серии:

| Режим | Ослабление обоих TX | Корректных эхо | Попыток | Время БС |
|---|---|---|---|---|

Сборка с предупреждениями как ошибками и независимый обзор изменений выполнены; автоматические
тесты по указанию пользователя не добавлялись и не запускались. Графики/диагностика в radiocom не включены.

### Обзорный спектр в широкой полосе (14.11.2026)

Выполнен один захват БС → UE: QPSK, MCS 0, ослабление TX 20 дБ, усиление RX 40 дБ,
несущая 2400 МГц. Передатчик сохранил штатные 3.84 MSPS и RF-полосу 3 МГц; только для внешней
диагностики приёмник настроен на 15.36 MSPS и RF-полосу 14 МГц. Записано 614400 комплексных
отсчётов (40 мс). Обзорный спектр охватывает 2392.32–2407.68 МГц, полезная полоса — примерно
2398.65–2401.35 МГц. Спектральная плотность усреднена по всей записи, включая паузы TDD;
уровни даны в дБFS/Гц, а не в калиброванных дБм.

После фильтрации и уменьшения частоты дискретизации записи в четыре раза штатный PHY нашёл кадр
и независимо декодировал **4/4 транспортных блока**, CRC и байты нагрузки верны; оценка CFO −12.764 кГц.
Это результат одного направления и одного найденного кадра, не серия эхо-обменов.
На спектре обнаружен сильный пик около 2404 МГц вне полезной полосы; его источник не установлен.
Пиковая компонента I/Q достигла 0.997 от полной шкалы, поэтому запас до насыщения мал;
отсчётов с модулем I или Q не менее 0.999 не было. Это не исключает перегрузку аналогового тракта.

Захват и построение графика выполнены временными внешними средствами; рабочие настройки программы
и её интерфейс не изменены. Передача завершена. I/Q для текущей отладки сохранены в
`/private/tmp/radiocom_wide.iq`, график — `wide-spectrum-mcs0.png` в каталоге визуализаций текущего чата;
временные файлы не являются постоянными артефактами репозитория.

## 8. Известные проблемы

- **Синхронизация ограничивает связь на слабом сигнале.** На 50 дБ один приём из четырёх оказался неверным из-за ошибки
  сдвига частоты, на 60 дБ слот не находится. Декодер способен на большее.
  Это наблюдение ранних опытов; для отказов обратного эхо MCS 16/17 при 20 дБ диагностика 14.11.2026
  не подтвердила начало кадра/постоянный частотный сдвиг как достаточную причину (см. раздел 7).
- **Поднесущая 143** (индекс в сетке, около +810 кГц) стабильно давала ошибки во всех символах в опытах с Хэммингом.
  Причина не исследована (провал канала или узкополосная помеха). С турбокодом проблема не проявилась. Вероятное
  объяснение (08.11.2026): в шуме приёмника `fd95` без передачи постоянно виден узкий спур около +796 кГц; с учётом
  сдвига частот −12.5 кГц это как раз поднесущая +810 кГц. Требует отдельной проверки.
- **Отдельные всплески до −12…−25 дБFS** длительностью около 1 мс в случайных местах записи без передачи — посторонние
  сигналы в ISM 2.4 ГГц (вероятно, Wi‑Fi). На усилении 65–70 дБ их больше, общий шум выше.
- **Краевая мощность в спектре.** При мощной передаче по краям принимаемой полосы (около ±1.9 МГц) появляется энергия
  на 20 дБ выше кадра; без передачи её нет. Причина не найдена (возможно, нелинейность или образы на передатчике).
- **Pluto-передатчик может перестать открываться** после серии быстрых запусков (см. раздел 2).
- **Посторонний сигнал около +92…94 кГц** на приёмнике без передачи (источник не известен), описан в `sdr_txrx_test.md`.
- **Сборка с AFF3CT** добавляет около полутора минут; CI на ubuntu и macOS пока не проверялся.

## 9. Что планируется дальше

Порядок примерный; в начале то, что даёт наибольший эффект. ARQ/HARQ и повторные отправки
по ошибке относятся только к будущему отдельно согласованному этапу; в текущем обмене они запрещены.

1. **Надёжность синхронизации.** Сделать приём устойчивым на 50–60 дБ: усреднение корреляции по нескольким
   повторам слота или проверка слота по CRC и выбор следующего пика, если CRC не прошла; более точная оценка
   сдвига частоты (в том числе по CRS).
2. **Несколько слотов и кадр 10 мс.** 20 слотов, номер слота n_s влияет на последовательность CRS (6.10.1.1) и на
   скремблирование (6.3.1); PSS в слотах 0 и 10; добавить SSS и номер ячейки N_ID^cell = 3·N_ID^(1) + N_ID^(2)
   (корни PSS 25, 29, 34, табл. 6.11.1.1-1). Нужны страницы TS 36.211: SSS (6.11.2), структура кадра (4.1).
3. **Двусторонний обмен.** Автоматический пинг-понг с эхо реализован и проверен 14.11.2026 (разделы 3 и 7).
   Следующий шаг — простой протокол подключения: сигнал синхронизации, случайный доступ
   (преамбулы PRACH на последовательностях Задова–Чу, TS 36.211 разд. 5.7 по `LTE_report.md`), ответ БС.
4. **Каналы управления.** Сверточный код с tail-biting для управляющей информации (BCH, DCI): скорость 1/3, полиномы
   133, 171, 165, TS 36.212 5.1.3.1, рис. 5.1.3-1, согласование скорости 5.1.4.2. В AFF3CT есть нерекурсивный
   сверточный кодер с произвольными полиномами и декодер Витерби, но его завершение нулевыми битами, а не tail-biting.
   В IT++ (GPL-3.0) tail-biting есть (`encode_tailbite`, `decode_tailbite`). Нужно решить, чем пользоваться. Нужны
   страницы 36.212 5.1.3.1 (рис. 5.1.3-1) и 5.1.4.2.
5. **Модуляции и скорости.** 16QAM, 64QAM, MCS 0–28 и сегментация сделаны и проверены по эфиру (раздел 4, п. 10;
   раздел 7). Дальше: устойчивость к всплескам Wi‑Fi (повтор или HARQ с версиями избыточности), выбор MCS по оценке
   SNR на приёме.
6. **Сверка допущений** (раздел 6): N_IR и N_cb, порядок бит в байте.
7. **Исследовать поднесущую 143 и краевую мощность** (разведением антенн, изменением частоты LO, спектром без передачи).
8. **Отчётные материалы** (после рабочей системы): графики BER и BLER от SNR; для этого нужны оценка SNR на приёме по
   принятому кадру и ступени мощности передатчика (шаг по 10 дБ или мельче).
9. **Автоматические тесты отложены.** По указанию пользователя от 14.11.2026 новые тесты не добавляем;
   проверяем сборкой, промежуточными запусками по эфиру и отладочными графиками вне программы.
10. **Протокол и архитектура.** После двустороннего обмена решить, нужны ли отдельные процессы БС и абонента с разными
    наборами функций, и как протокол подключения использует слоты.

## 10. Как проверялось и как проверить заново

Тестовые программы использовали внутренние функции `SignalManipulation.cpp` через `#include` самого файла `.cpp`
(теперь эти функции объявлены в `Ofdm.h` и `ChannelCoding.h`, их можно подключать как обычные заголовки).

- **CRC:** вход «123456789» (байты, старший бит первым), ожидаемый остаток 0xCDE703; остаток после присоединения CRC равен 0.
- **Турбокод:** независимый кодер по рис. 5.1.3-2: регистры s0, s1, s2; обратная связь a = c ⊕ s1 ⊕ s2, чётность
  z = a ⊕ s0 ⊕ s2, сдвиг; завершение подачей бита s1 ⊕ s2 три шага; интерливер Π(i) = (f1·i + f2·i²) mod K (для 672:
  f1 = 43, f2 = 252); потоки собираются по формулам 5.1.3.2.2. Сравнить с выходом `TurboCodec::Encode` для случайного блока.
- **Согласование скорости:** прямая реализация шагов 5.1.4.1.1 (матрица R × 32, строки, перестановка столбцов, чтение по
  столбцам, формула для d(2)) и 5.1.4.1.2 (кольцевой буфер, k0, выбор E бит). Сравнить с `buildRateMatchingMap`.
- **Сквозная синтетика:** слот из `Modulate`, поворот фазы, затухание 0.7, сдвиг частоты около −12.5 кГц, шум;
  `FindSync` и `Demodulate`; счёт успешных декодирований при разных SNR.
- **QAM:** `pdftotext -layout` по `ts_136211v160200p-2.pdf`, разбор строк табл. 7.1.3-1 и 7.1.4-1 (знак «−» бывает
  отделён пробелом, а `splitlines()` в Python режет и по символу перевода страницы — нумерация строк уезжает),
  сравнение с `mapBits` для каждой группы бит, умноженной на √10 или √42.
- **По эфиру:** запуск `bs` и `ue` (раздел 3) на ослаблениях 40, 50, 60 дБ; для анализа записи `rx.iq` сохраняются.

## 12. Приложение: как сигнал проходит через Pluto

Этап 1. Биты → символы (модуляция)

"hello" → биты 01101000 01100101 ... → группируются по 2 бита (QPSK) или по 4/6 бит (16QAM/64QAM) → каждая группа превращается в одну комплексную точку на созвездии (число вида I + jQ).

Результат этапа: поток комплексных чисел. Это ещё не сигнал, а просто числа в памяти компьютера.

Этап 2. Символы → baseband-сигнал (цифровой, в низкой полосе)

Эти комплексные числа "растягивают" во времени (формирование импульса, pulse shaping) и получают поток IQ-отсчётов — это и есть тот самый цифровой сигнал, который живёт "около нуля Гц".

Вот тут работает Sample Rate. Sample Rate — это буквально "сколько таких IQ-чисел в секунду". Чем выше Sample Rate, тем шире полоса, которую можно уместить в этот цифровой поток (по теореме Найквиста: доступная полоса ≈ Sample Rate).

Этап 3. ЦАП (DAC) — из чисел в аналоговое напряжение

Pluto превращает поток IQ-чисел в реальное аналоговое напряжение. Здесь Sample Rate — это ещё и буквально скорость работы ЦАП (сколько раз в секунду он выдаёт новое значение напряжения).

Этап 4. Перенос на несущую частоту (mixer, "upconversion")

Aналоговый baseband-сигнал (который "около нуля") умножается на несущую частоту гетеродина (LO) — и переезжает туда, куда вы выставили Center Frequency (в наших опытах 2.4 ГГц). Это буквально сдвиг сигнала по оси частот вверх, в радиодиапазон.

Этап 5. Аналоговый фильтр (это и есть Bandwidth / rf_bandwidth)

После переноса на несущую сигнал проходит через аналоговый фильтр, который отсекает всё лишнее за пределами нужной полосы (шум, соседние каналы). Вот что такое "Bandwidth" в настройках — это ширина именно этого фильтра, в аналоговой части, уже на радиочастоте.

Этап 6. Антенна → эфир

Сигнал излучается.
