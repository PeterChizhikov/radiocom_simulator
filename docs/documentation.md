## 1. Цель и принятые решения

Система для двусторонней линии связи между базовой станцией (БС, eNodeB) и абонентом (UE) на двух Pluto SDR по мотивам
LTE: собственный упрощённый физический уровень, повторяющий LTE Rel-8 там, где это возможно, и упрощённый протокол
подключения абонента к БС. Программного симулятора больше нет: он был удалён, все результаты получаются через эфир.
Отчётные материалы (графики BER/BLER от SNR, измерения для курсовой) делаются **после** того, как система заработает.

| Параметр | Решение |
|---|---|
| Язык | C++20, весь код ядра |
| Уровни | физический уровень + упрощённый протокол подключения абонента к БС |
| Дуплекс | TDD (время делится между приёмом и передачей на одной частоте) |
| Работа по эфиру | пинг-понг «передал, переключился, принял» (см. раздел 9); жёсткая сетка субкадров по времени на Pluto невозможна, так как данные идут через USB с плавающей задержкой |
| Полезная нагрузка | тестовые данные, не реальный IP-трафик |
| Работа с SDR | libiio (C API) напрямую |
| Частота | 2.4 ГГц (ISM) |
| Полоса и частота дискретизации | LTE 3 МГц: 3.84 MSPS, БПФ 256, 180 поднесущих |
| Мощность передачи | начинать с минимальной, поднимать шагами по 10 дБ; ослабление TX не меньше 40 дБ (ограничено в коде) |
| Готовые библиотеки | кодирование берём готовое: AFF3CT (MIT) для турбокода; своё не пишем |
| Процессы | одна программа, роль выбирается флагом (`--role bs` или `--role ue`), один процесс на каждый Pluto |
| Подход | двигаться маленькими шагами, каждый проверять по эфиру или независимым эталоном; формулы и константы брать из стандарта и записывать пункт в комментарии |

UI (веб-интерфейс) планировался раньше, сейчас не развивается.

## 2. Оборудование и безопасность

Два ADALM-Pluto, подключены к одному компьютеру по USB, антенны на расстоянии нескольких сантиметров:

| Роль | Чип | Серийный номер | URI на 18.10.2026 | Антенна |
|---|---|---|---|---|
| Передатчик (БС) | AD9361, 2x2 | `104000409f94…` | `usb:1.3.5` | TX1 |
| Приёмник (UE) | AD9364, 1x1 | `10400090fd95…` | `usb:1.4.5` | RX1 |

- **URI меняются** после переподключения. Роли определять по серийным номерам: `iio_info -s`.
- В документах `pluto_info.md` и `sdr_txrx_test.md` URI одного и того же серийного номера записаны по-разному, так как
  снимались в разное время. Верить текущему выводу `iio_info -s`.
- Один раз Pluto-передатчик перестал открываться (`Failed to reset pipes: Input/output error`) после серии быстрых
  запусков и остановок передачи. Помогло переподключение USB.
- Расхождение частот двух Pluto около **−12.5 кГц** на 2.4 ГГц (около −5 ppm), почти одна поднесущая (15 кГц).
  Дрейф по температуре в больших интервалах не измерялся.
- Расстояние между антеннами критично: разведение антенн ухудшает связь примерно на **20 дБ** (тон падал с 54 дБ до
  33 дБ над шумом при том же ослаблении).

**Защита приёмного тракта** (в `Sdr.cpp`, не отключать): при старте ослабление TX ставится на максимум (89.75 дБ),
значения ниже 40 дБ отклоняются, при выходе передача останавливается и ослабление возвращается на максимум. Повредить
вход приёмника может только мощность на входе RX; усиление RX влияет лишь на клиппинг АЦП.

## 3. Структура проекта и как запускать

Все модули в `src/modules/<Модуль>/`: заголовок и `.cpp` рядом, один CMake-таргет на модуль.

| Модуль | Назначение |
|---|---|
| `Common` | типы `Sample_t`, `Signal_t`, `Bytes_t` |
| `Logger` | интерфейс `ILogger`, реализация на spdlog |
| `SignalFileIO` | сохранение и загрузка I/Q в файл (float32, как `gr_complex`), нужно для разбора записей `rx.iq` |
| `SignalManipulation` | физический уровень: интерфейс `IPhyLayer` (`Modulate`, `FindSync`, `Demodulate`, `GetPayloadSize`) |
| `Sdr` | `PlutoDevice`: настройка и передача/приём через libiio |
| `src/main.cpp` | запускатель системы с ролями `bs` и `ue` |
| `src/txrx.cpp` | первый аппаратный тест: передача и приём тона |

Сборка (при первой конфигурации нужна сеть: скачиваются spdlog и AFF3CT; AFF3CT добавляет около полутора минут к
чистой сборке):

```bash
cmake -B build -DCMAKE_BUILD_TYPE=Release        # -DRADIOCOM_WARNINGS_AS_ERRORS=ON, чтобы предупреждения были ошибками
cmake --build build
```

Запуск (передатчик в одном терминале, приёмник в другом; передача идёт, пока не нажат Enter):

```bash
./build/radiocom --role bs --uri usb:1.3.5 --tx-atten 40
./build/radiocom --role ue --uri usb:1.4.5 --rx-gain 50 --output rx.iq
./build/radiocom_txrx --tx usb:1.3.5 --rx usb:1.4.5 --tx-atten 50 --rx-gain 50   # тест с тоном
```

`ue` выводит: уровень приёма, начало слота и сдвиг частоты, число ошибок кодовых бит до декодирования и признак
«CRC верна, сообщение верное». Ключ `-v` включает подробный журнал.

Зависимости: CMake, компилятор C++20, FFTW3 (`brew install fftw`), libiio (`brew tap tfcollins/formulae &&
brew install libiio`; на macOS поиск через `find_library`, так как `libiio.pc` сломан), spdlog и AFF3CT скачиваются сами.

## 4. Что сделано и проверено

Порядок соответствует хронологии работы.

1. **Тон через эфир** (этап 1). Управление Pluto из C++, циклическая передача тона +100 кГц, приём 65536 отсчётов, поиск
   пика в спектре. Измерен сдвиг частоты между двумя Pluto. Результаты в `sdr_txrx_test.md`.
2. **Симулятор убран.** Удалены `SimulationCore`, канал AWGN, цикл по SNR, `plotBER_SBR.py`. `main.cpp` стал
   запускателем ролей. Модуль `SignalManipulation` разделён на «байты в отсчёты» и «отсчёты в байты».
3. **Первый кадр через эфир** (Хэмминг, QPSK, один OFDM-символ). Показал, что кадр слабый (около −30 дБFS из-за
   деления на N при IFFT); `main.cpp` теперь масштабирует передаваемый кадр до пика 0.5, как у проверенного тона.
4. **Сигнал синхронизации PSS** (Задова–Чу, корень 25, 62 элемента) и поиск кадра кросс-корреляцией. По эфиру находится.
5. **Оценка сдвига частоты.** Сдвиг смещает пик корреляции Задова–Чу по времени (около 100–150 отсчётов при 12 кГц),
   поэтому сначала перебираются гипотезы сдвига от −15 до +15 кГц с шагом 3 кГц, затем уточнение по разности фаз
   корреляций двух половин PSS. Точность оценки в синтетике: меньше 50 Гц; по эфиру −12.2…−12.8 кГц.
6. **Сетка LTE на 3 МГц и слот.** 15 RB, 180 поднесущих (−90…−1, +1…+90, DC пустая), слот из 7 символов,
   CP 20 у символа 0 и 18 у остальных, слот 1920 отсчётов. PSS в последнем символе слота (как в LTE FDD).
7. **Пилоты CRS и оценка канала.** Пилоты порта 0 в символах 0 и 4, каждая 6-я поднесущая (в символе 4 со сдвигом 3),
   значения из последовательности Голда. Оценка канала: деление принятого на известное в пилотах, интерполяция по
   частоте, затем по времени между символами 0 и 4. Убрало случайный поворот созвездия (до этого 15–50 % ошибок).
8. **Турбокод LTE** через AFF3CT вместо Хэмминга. Цепочка: CRC24A, турбокод, согласование скорости, скремблирование,
   QPSK. На приёме мягкие значения, обратные операции, декодер AFF3CT (6 итераций), проверка CRC.
9. **Хэмминг удалён** (код и файл `Hamming.h`).

Тестовые программы лежали во временном каталоге и в проект не входят; методика в разделе 10.

## 5. Физический уровень: что откуда взято

Цепочка передачи: нагрузка 81 байт → CRC24A → один кодовый блок K = 672 → турбокод → согласование скорости до E = 2040
бит → скремблирование → QPSK → ресурсная сетка 7 × 180 → OFDM (обратное БПФ 256, циклический префикс) → слот 1920
отсчётов. Приём: поиск слота по PSS и сдвиг частоты → БПФ по символам → оценка канала по CRS → мягкие значения →
снятие скремблирования → обратное согласование скорости → турбодекодер → проверка CRC.

| Что | Документ и пункт | Где в коде |
|---|---|---|
| 15 RB, 180 поднесущих для 3 МГц, БПФ 256 | `LTE_report.md`, п. 4.5–4.6 (TS 36.101 табл. 5.6-1; БПФ и частота 3.84 МГц — инженерное соглашение, не норма) | константы сетки |
| Поднесущие −90…−1, +1…+90, DC не используется | TS 36.211 V16.2.0, 6.12 | `frequencyBin` |
| CP 160 для l = 0 и 144 для l = 1…6 (при N = 2048), то есть 20 и 18 при N = 256 | TS 36.211 V16.2.0, табл. 6.12-1 | `cyclicPrefixLength` |
| PSS: формула d_u(n), корень 25 (N_ID^(2) = 0) | TS 36.211 V16.2.0, 6.11.1.1, табл. 6.11.1.1-1 | `generateSyncSequence` |
| PSS: отображение k = n − 31 + 90, последний символ слота 0 | TS 36.211 V16.2.0, 6.11.1.2 | `mapSyncSignal` |
| Последовательность Голда, N_c = 1600 | TS 36.211 V16.2.0, 7.2 | `generateGoldSequence` |
| CRS: r(m), c_init, нормировка 1/√2 | TS 36.211 V16.2.0, 6.10.1.1 | `generateReferenceSequence` |
| CRS: k = 6m + (v + v_shift) mod 6, символы l = 0 и 4, m′ = m + N_RB^max − N_RB | TS 36.211 V16.2.0, 6.10.1.2 | `mapReferenceSignals`, `referenceShift` |
| CRC24A, порядок бит, p0 — старший бит остатка | TS 36.212 V15.2.1, 5.1.1 | `calculateCrc`, `attachCrc` |
| Турбокод: g0 = 1 + D² + D³, g1 = 1 + D + D³, 8 состояний | TS 36.212 V15.2.1, 5.1.3.2.1 | `TurboCodec` (AFF3CT) |
| Хвостовые биты и потоки d(0), d(1), d(2) длины K + 4 | TS 36.212 V15.2.1, 5.1.3.2.2 | `TurboCodec::buildLayout` |
| Интерливер QPP, таблица 5.1.3-3 | TS 36.212 V15.2.1, 5.1.3.2.3 | интерливер LTE в AFF3CT |
| Интерливер подблоков: 32 столбца, перестановка столбцов, формула для d(2) | TS 36.212 V15.2.1, 5.1.4.1.1, табл. 5.1.4-1 | `buildRateMatchingMap` |
| Кольцевой буфер, k0, выбор E бит с пропуском NULL | TS 36.212 V15.2.1, 5.1.4.1.2 | `buildRateMatchingMap` |
| E = N_L · Q_m · ⌊G′/C⌋ (один блок, один слой, QPSK) | TS 36.212 V15.2.1, 5.1.4.1.2 | конструктор `PhyLayer` |
| Скремблирование, c_init для PDSCH | TS 36.211, 6.3.1 | `scramblingInit` |
| Размер блока K = 672 из таблицы, сегментации нет | TS 36.212 V15.2.1, табл. 5.1.3-3; 5.1.2 | `codeBlockSize` |

Страницы стандарта, по которым сверялась реализация, присылались скриншотами. Более ранние пометки ⚠️ в
`LTE_report.md` частично закрыты: длины CP для DL, DC-поднесущая, отображение PSS и формулы CRS теперь сверены (см. также
раздел 6 про то, что осталось).

## 6. Допущения, не взятые из стандарта

Эти места нужно знать и при необходимости сверить:

- **Порядок бит в байте нагрузки:** старший бит первым. В присланных страницах порядок не определён.
- **n_RNTI = 1:** значение выбрано в проекте.
- **N_cb = K_w:** размер кольцевого буфера принят полным; формула с N_IR (мягкий буфер приёмника по категории UE) в
  проекте не применялась (5.1.4.1.2).
- **6 итераций** турбодекодера выбраны в проекте.
- **Отображение QPSK** (b(2i) задаёт I, b(2i+1) задаёт Q, 0 даёт плюс): TS 36.211, 7.1.2; записано по памяти,
  страница не сверена. Совпадает с тем, что было в коде с самого начала.
- **Номер слота n_s = 0 всегда:** передаётся один и тот же слот, поэтому CRS и скремблирование не меняются.
- **Одна ячейка:** N_ID^cell = 0, корень PSS 25. В символе с PSS остальные поднесущие не несут данных (в LTE они могут
  быть заняты PDSCH, правила в 36.211 6.3.5 не изучались).
- **Размер E:** все 1020 ресурсных элементов слота отданы под один кодовый блок; в LTE слот был бы частью субкадра из
  двух слотов, PBCH и управляющие каналы не учитываются.
- **Размер блока и частота 3.84 МГц:** инженерное соглашение (отчёт, п. 4.6).

## 7. Результаты измерений по эфиру

Антенны на расстоянии нескольких сантиметров, усиление приёма 50 дБ, передатчик `usb:1.3.5`, приёмник `usb:1.4.5`.

**Слот с турбокодом (81 байт):**

| Ослабление TX | Корреляция PSS | Ошибок кодовых бит до декодирования | Сообщение принято верно |
|---|---|---|---|
| 40 дБ | 0.87–0.89 | 6–12 из 2040 (0.3–0.6 %) | 5 из 5 |
| 50 дБ | 0.53–0.56 | 254–774 из 2040 (12–38 %) | 3 из 4 |
| 60 дБ | 0.26–0.28 | около 1000 из 2040 (половина) | 0 из 4, слот не найден |

На 50 дБ турбокод исправляет 12–14 % ошибок; неудачный приём был вызван неверным сдвигом частоты при синхронизации
(−13.2 кГц вместо −12.7 кГц), а не слабостью декодера. На 60 дБ ограничивает поиск слота по PSS.

**Сравнение с Хэммингом** (тот же канал, 40 дБ): ошибок 5–14 из 2032, декодирование успешно в 1 из 5 приёмов, так как
ошибка символа QPSK портила оба бита одного блока Хэмминга.

**Тон** (`radiocom_txrx`): 54.5 дБ над шумом при 50 дБ и антеннах рядом; 33 дБ при разведённых антеннах; сдвиг
частоты −9.8…−12.8 кГц от опыта к опыту. Ранние результаты (один Pluto и два Pluto) в `sdr_txrx_test.md`.

## 8. Известные проблемы

- **Синхронизация ограничивает связь на слабом сигнале.** На 50 дБ один приём из четырёх оказался неверным из-за ошибки
  сдвига частоты, на 60 дБ слот не находится. Декодер способен на большее.
- **Поднесущая 143** (индекс в сетке, около +810 кГц) стабильно давала ошибки во всех символах в опытах с Хэммингом.
  Причина не исследована (провал канала или узкополосная помеха). С турбокодом проблема не проявилась.
- **Краевая мощность в спектре.** При мощной передаче по краям принимаемой полосы (около ±1.9 МГц) появляется энергия
  на 20 дБ выше кадра; без передачи её нет. Причина не найдена (возможно, нелинейность или образы на передатчике).
- **Pluto-передатчик может перестать открываться** после серии быстрых запусков (см. раздел 2).
- **Посторонний сигнал около +92…94 кГц** на приёмнике без передачи (источник не известен), описан в `sdr_txrx_test.md`.
- **Сборка с AFF3CT** добавляет около полутора минут; CI на ubuntu и macOS пока не проверялся.

## 9. Что планируется дальше

Порядок примерный; в начале то, что даёт наибольший эффект.

1. **Надёжность синхронизации.** Сделать приём устойчивым на 50–60 дБ: усреднение корреляции по нескольким
   повторам слота или проверка слота по CRC и выбор следующего пика, если CRC не прошла; более точная оценка
   сдвига частоты (в том числе по CRS).
2. **Несколько слотов и кадр 10 мс.** 20 слотов, номер слота n_s влияет на последовательность CRS (6.10.1.1) и на
   скремблирование (6.3.1); PSS в слотах 0 и 10; добавить SSS и номер ячейки N_ID^cell = 3·N_ID^(1) + N_ID^(2)
   (корни PSS 25, 29, 34, табл. 6.11.1.1-1). Нужны страницы TS 36.211: SSS (6.11.2), структура кадра (4.1).
3. **Двусторонний обмен.** Пинг-понг: БС передала, абонент принял и ответил (TDD по часам невозможен из-за задержки USB).
   Сначала один слот туда и один обратно, затем простой протокол подключения: сигнал синхронизации, случайный доступ
   (преамбулы PRACH на последовательностях Задова–Чу, TS 36.211 разд. 5.7 по `LTE_report.md`), ответ БС.
4. **Каналы управления.** Сверточный код с tail-biting для управляющей информации (BCH, DCI): скорость 1/3, полиномы
   133, 171, 165, TS 36.212 5.1.3.1, рис. 5.1.3-1, согласование скорости 5.1.4.2. В AFF3CT есть нерекурсивный
   сверточный кодер с произвольными полиномами и декодер Витерби, но его завершение нулевыми битами, а не tail-biting.
   В IT++ (GPL-3.0) tail-biting есть (`encode_tailbite`, `decode_tailbite`). Нужно решить, чем пользоваться. Нужны
   страницы 36.212 5.1.3.1 (рис. 5.1.3-1) и 5.1.4.2.
5. **Модуляции и скорости.** 16QAM и 64QAM (TS 36.211 7.1), выбор MCS и размер транспортного блока (TS 36.213 7.1.7),
   сегментация блоков больше 6144 бит (TS 36.212 5.1.2), версии избыточности и HARQ.
6. **Сверка допущений** (раздел 6): страница TS 36.211 7.1.2, N_IR и N_cb, порядок бит в байте.
7. **Исследовать поднесущую 143 и краевую мощность** (разведением антенн, изменением частоты LO, спектром без передачи).
8. **Отчётные материалы** (после рабочей системы): графики BER и BLER от SNR; для этого нужны оценка SNR на приёме по
   принятому кадру и ступени мощности передатчика (ослабление не ниже 40 дБ, шаг по 10 дБ или мельче).
9. **Тесты в проекте.** Проверки из раздела 10 сейчас лежат вне проекта. Стоит оформить их как тесты в репозитории
   (контрольное значение CRC, эталонный турбокодер, сравнение карты согласования скорости, сквозной тест с синтетическим
   каналом) и подключить к CI.
10. **Протокол и архитектура.** После двустороннего обмена решить, нужны ли отдельные процессы БС и абонента с разными
    наборами функций, и как протокол подключения использует слоты.

## 10. Как проверялось и как проверить заново

Тестовые программы использовали внутренние функции `SignalManipulation.cpp` через `#include` самого файла `.cpp`.

- **CRC:** вход «123456789» (байты, старший бит первым), ожидаемый остаток 0xCDE703; остаток после присоединения CRC равен 0.
- **Турбокод:** независимый кодер по рис. 5.1.3-2: регистры s0, s1, s2; обратная связь a = c ⊕ s1 ⊕ s2, чётность
  z = a ⊕ s0 ⊕ s2, сдвиг; завершение подачей бита s1 ⊕ s2 три шага; интерливер Π(i) = (f1·i + f2·i²) mod K (для 672:
  f1 = 43, f2 = 252); потоки собираются по формулам 5.1.3.2.2. Сравнить с выходом `TurboCodec::Encode` для случайного блока.
- **Согласование скорости:** прямая реализация шагов 5.1.4.1.1 (матрица R × 32, строки, перестановка столбцов, чтение по
  столбцам, формула для d(2)) и 5.1.4.1.2 (кольцевой буфер, k0, выбор E бит). Сравнить с `buildRateMatchingMap`.
- **Сквозная синтетика:** слот из `Modulate`, поворот фазы, затухание 0.7, сдвиг частоты около −12.5 кГц, шум;
  `FindSync` и `Demodulate`; счёт успешных декодирований при разных SNR.
- **По эфиру:** запуск `bs` и `ue` (раздел 3) на ослаблениях 40, 50, 60 дБ; для анализа записи `rx.iq` сохраняются.

## 12. Приложение: как сигнал проходит через Pluto

Этап 1. Биты → символы (модуляция)

"hello" → биты 01101000 01100101 ... → группируются по 2 бита (QPSK) или по 4/6 бит (16QAM/64QAM) → каждая группа превращается в одну комплексную точку на созвездии (число вида I + jQ).

Результат этапа: поток комплексных чисел. Это ещё не сигнал, а просто числа в памяти компьютера.

Этап 2. Символы → baseband-сигнал (цифровой, в низкой полосе)

Эти комплексные числа "растягивают" во времени (формирование импульса, pulse shaping) и получают поток IQ-отсчётов — это и есть тот самый цифровой сигнал, который живёт "около нуля Гц".

Вот тут работает Sample Rate. Sample Rate — это буквально "сколько таких IQ-чисел в секунду". Чем выше Sample Rate, тем шире полоса, которую можно уместить в этот цифровой поток (по теореме Найквиста: доступная полоса ≈ Sample Rate).

Этап 3. ЦАП (DAC) — из чисел в аналоговое напряжение

Pluto превращает поток IQ-чисел в реальное аналоговое напряжение. Здесь Sample Rate — это ещё и буквально скорость работы ЦАП (сколько раз в секунду он выдаёт новое значение напряжения).

Этап 4. Перенос на несущую частоту (mixer, "upconversion")

Aналоговый baseband-сигнал (который "около нуля") умножается на несущую частоту гетеродина (LO) — и переезжает туда, куда вы выставили Center Frequency (в наших опытах 2.4 ГГц). Это буквально сдвиг сигнала по оси частот вверх, в радиодиапазон.

Этап 5. Аналоговый фильтр (это и есть Bandwidth / rf_bandwidth)

После переноса на несущую сигнал проходит через аналоговый фильтр, который отсекает всё лишнее за пределами нужной полосы (шум, соседние каналы). Вот что такое "Bandwidth" в настройках — это ширина именно этого фильтра, в аналоговой части, уже на радиочастоте.

Этап 6. Антенна → эфир

Сигнал излучается.
