
Дисклеймер

Раздел **"Стили"** предназначен для написания **новых сущностей** в проекте. При внесении изменений в существующих сущностях проекта, рекомендуется придерживаться стиля использованного при написании редактируемого класса/структуры.

**Документ предназначен для написания кода на языке C++.** Для C справедливы именования функций, структур, переменных, общие положения по **Includes** и **Control Flow**
# Стили

#### PascalCase для

- namespaces
- structs
- classes
- enums
- enum elements
- type aliases
- template parameters
- public methods

#### camelCase для

- free functions
- private methods
- local variables
- global variables
- struct/class static variables
- struct/class fields
- function arguments

#### Именования

- Поля классов должны иметь префикс **m_***.
- Все getters/setters начинаются со слова **get***/**set***.
- Функции должны иметь глагол в имени для облегчения понимания, что они делают.
- Интерфейсы начинаются с буквы **I***, а абстрактные классы идут с ***Base** постфиксом.
- Для имен типов добавляется постфикс **_t**

# Семантика

### struct vs class

Использование структур:

- если все поля public
- любые комбинации полей валидны
- деструктор default

В остальных случаях используются классы.

### Переменные

- Объявление переменных должно располагаться максимально близко к их использованию.
- Лучше создать новую const переменную, чем использовать предыдущую для хранения результатов вызова функций.
- Необходимо инициализировать примитивы при объявлении (_int, float, array of int, etc._). Если переменная не модифицируется, то должна быть объявлена как const.
- Global mutable переменные не рекомендуется использовать.
- _int8_t, uint_8t, int16_t, uint16_t etc._ типы должны быть использованы вместо платформо-специфичных _BYTE/WORD/DWORD_.
- size_t должен использоваться для счетчиков, переменных, обозначающих размер и т.д.
- std::byte для представления сырых данных.
- auto должен использоваться когда тип данных ясен из контекста.
- Следует использовать только префиксные операторы инкремента и декремента (++, --)

### Аргументы функций

- Передача по значению: для примитивов или структур и классов, которые не обходятся дорого в копировании. Либо, если копирование в рамках функции необходимо для локального редактирования данных без изменений с вызывающей стороны.
- Указатели используются для опциональной передачи, если аргумент может быть null.
- В остальных случаях используется передача по ссылке (const в случаях, если не предусматривается модификация аргумента внутри функции).

### Приведение типов

- Function-style cast для integer/float типов, static_cast и reinterpret_cast для указателей и ссылок.
- Стараться минимизировать приведения между числовыми типами.
- const-cast лучше обходить стороной и по возможности менять архитектуру кода.
- Force-casting _int to bool_, _pointer to bool_ лучше обходить, вместо этого использовать «!=0 или !=nullptr».
- nullptr вместо NULL для указателей.

### Control flow

- Использование Goto исключено для C++ кода. В C может встречаться, если другие решения приводят к драматическому усложнению кода.
- По возможности использовать range-for вместо for со счетчиком.
- Не использовать else, после if с return для уменьшения вложенности кода.
- Предпочтительнее использовать swtich-case вместо if-else конструкций, где возможно.
- Все локальные переменные, структуры и классы фундаментальных типов, которые имеют инициализацию по умолчанию должны быть инициализированы.
- Использовать свободные функции, вместо класса, если в классе или его методе нет необходимости
- Ширина строки кода должна не превышать 120 символов для улучшения читабельности кода
- Тело if должно идти на следующей строке, чтобы избегать однострочных if блоков, т.к. они не очень удобны для чтения

### Работа с памятью

- По возможности использовать std::shared_ptr/std::unique_ptr для единичных объектов, std::vector для динамических массивов и обходить сырые указатели при передаче владения (для этого есть std::unique_ptr).
- Нужно использовать RAII-классы std::lock_guard/std::unique_lock вместо ручных lock/unlock вызовов мьютекса.
- Если потребовался std::lock для одновременной блокировки нескольких мьютексов, то лучше постараться пересмотреть архитектуру кода, чтобы его использование не было необходимым.
- Лучше создавать RAII классы для lifetime-контроля ресурсов, вместо вызовов free/release/delete.
- Лучше использовать std::memcpy для копирования "сырых байтовых" данных.
- Если нужно выделить массив непрерывной памяти - не использовать чистое выделение через new, лучше
    - использовать std::array для создания массива со статичным размером
    - std::vector для изменяемого массива
    - в крайнем случае оборачивать new в std::unique_ptr

### Списки инициализации

Если список инициализации состоит из нескольких элементов, то следует придерживаться следующей семантики

**Пример оформления списка инициализации**

|                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------------------------------------- |
| `Foo::Foo()`<br><br>    `: BaseFoo()`<br><br>    `, m_field(``false``)`<br><br>    `, m_var(0)`<br><br>`{`<br><br>`...`<br><br>`}` |

### RAII

**Методы RAII класса:**

- конструктор (берет владение над сырыми ресурсами)
- конструктор перемещения (должен быть noexcept)
- оператор перемещения (должен быть noexcept)
- деструктор (освобождает ресурсы)

**Должны быть удалены:**

- конструктор копирования
- оператор копирования

**Пример RAII для управления ресурсами HANDLE:**

|   |
|---|
|`class` `UniqueHandle`<br><br>`{`<br><br>`public``:`<br><br>    `using` `CloseFunc =` `BOOL``(WINAPI*)(``HANDLE``);`<br><br>`public``:`<br><br>    `UniqueHandle() =` `default``;`<br><br>    `UniqueHandle(``HANDLE` `handle, CloseFunc close_func);`<br><br>    `~UniqueHandle();`<br><br>    `UniqueHandle(``const` `UniqueHandle& other) =` `delete``;`<br><br>    `UniqueHandle(UniqueHandle&& other) noexcept;`<br><br>    `UniqueHandle& operator=(``const` `UniqueHandle& other) =` `delete``;`<br><br>    `UniqueHandle& operator=(UniqueHandle&& other) noexcept;`<br><br>    `HANDLE` `getHandle()` `const` `{` `return` `m_handle; }`<br><br>    `bool` `isValid()` `const` `{` `return` `m_handle != INVALID_HANDLE_VALUE; }`<br><br>`private``:`<br><br>    `HANDLE` `m_handle = INVALID_HANDLE_VALUE;`<br><br>    `CloseFunc m_close_func = nullptr;`<br><br>`};`|

### Функции и методы

- Лучше избегать больших lambda-выражений (более 5-10 строк кода), вместо них лучше использовать свободные функции. С осторожностью относиться к захвату this.
- Если функция используется только в одном cpp-файле, ее нужно обернуть в анонимный namespace.
- По возможности нужно стараться использовать “nothrow” версии std функций.

### Классы

- Конструктор класса не должен иметь код, который может вызвать exception или упасть. Вместо этого нужно использовать фабричный метод и возвращать из него std::nullopt/nullptr в случае ошибки. Не нужно использовать анти-паттерн инициализации, когда для инициализации класса необходимо вызывать метод Initialize. В таком случае, инициализация и/или проверки должны происходить в фабричном методе.
- При наличии аргументов в конструкторе по возможности использовать ключевое слово _explicit_ во избежание неявных приведений типов при создании объекта. Особенно важно, при передаче указателей на объект в качестве аргументов.
- Поля классов не должны быть public, для получения/записи значения поля используется getter/setter для обеспечения приемлемого уровня инкапсуляции.
- Предпочтительнее использовать инициализацию полей при объявлении, чем инициализацию полей в конструкторе.

### Порядок Includes

- текущие заголовки модуля (“”)
- заголовки проекта (“”)
- c++ std заголовки (<>)
- заголовки third-party библиотек (<>)

> После блока include’ов следует 2 пустых строки для выделения блока.

### Макросы

Вместо них лучше использовать свободные функции c рекомендательной директивой inline. Большинство небольших функций все равно будут вставлены в место вызова без использования vtable компилятором при сборке с оптимизацией. При этом их можно нормально отлаживать.

### Namespaces

Использовать для логического разделения функционала разных модулей/библиотек. using namespace по возможности не использовать, во избежание корявых ошибок с одинаковыми названиями функций.

> using namespace std – предать анафеме и забыть как страшный сон :)

### Global variables and objects

- Глобальные константы лучше создавать с constexpr взамен defines.
- Для общедоступных глобальных объектов лучше использовать паттерн Singleton без возможности его модификации после инициализации.

### Логирование

Ошибки необходимо заносить в лог с максимальной информацией о причинах их возникновения. Критические и серьезные ошибки, которые не сыплются десятками и более, должны записываться без включенной диагностики.

Также необходимо заносить в лог важные моменты, которые могут помогать при отладке и выяснении причин ошибочного поведения на стороне пользователя, но под уровнем TRACE, чтобы они писались только при включенной диагностике.
